# Backspace 아키텍처 참고 조사

확인일: 2026-10-06. GitHub 연결로 7개 저장소의 설명·문서와 관련 구현을 확인했다. 핵심 파일은 확인한 커밋으로 다시 읽었으며 경로, 커밋, blob SHA는 [조사 기록](github_reference_snapshot.json)에 저장했다. 저장소를 설치하거나 실행하지 않았다. 아래는 코드에서 확인한 동작과 Backspace에 적용할 설계 제안을 구분한 문서다. 각 저장소의 전체 구현·한국어 정확도·NVIDIA 호환성을 검증한 것은 아니다.

## 판단

현재 개선의 우선순위는 **문항에 필요한 구체적 설명을 보존하고, 실제 학습자료를 검색하여, 주장과 관계의 의미를 검증하는 것**이다. 에이전트 수나 그래프 크기를 늘리는 것만으로 해결되는 문제는 아니다. 강한 모델 단독보다 현재 시스템이 얼마나 낮은지는 동일 조건 비교 실험이 없어 아직 수치화할 수 없다.

현재 구현에서 직접 확인한 제한은 다음과 같다.

| 제한 | 현재 근거 | 결과와 개선 방향 |
|---|---|---|
| 문항 분석에 학습자료의 내용이 전달되지 않음 | `backspace_mvp/staged.py:158`: 문항·공통 지문·개념 이름·사고 코드만 입력 | 이름이 같아도 자료에 실린 설명을 활용할 수 없다. 검색한 원문 블록과 출처를 입력해야 한다. |
| 사고 단계 표현에 구체적인 입출력·성립 조건이 없음 | `staged.py:149`: 단계는 code와 label, 개념은 단계 하나에 연결 | 실제 저장된 1문항은 일반적인 사고 이름 6개다. 과학적 기작과 답안의 필수 요소를 별도로 보존해야 한다. |
| 인용 검증이 관계의 의미를 검증하지 않음 | `staged.py:110`, `staged.py:170`: 인용의 원문 포함 여부 검사 | 실제 `state/nvidia_live/dataset.json`에는 `세포호흡 → 산소 / part_of`가 들어갔다. 원문에 인용이 존재해도 이 관계를 뒷받침하지 않는다. |
| 개념별 연습이 구분되지 않음 | `analysis.py:124`: 연결된 문항의 모든 사고 코드를 해당 개념에 부여 | 문항 내에서 그 개념이 필요한 단계·설명 목표만 연결해야 한다. |
| 계획이 고정 문장 조립 | `pipeline.py:148`: 개념 이름과 사고 코드로 문자열 생성 | 같은 문항의 네 개념에 거의 같은 활동이 생긴다. 산출물·통과 기준·근거 문항을 갖춘 과제로 바꿔야 한다. |

예외 처리·작은 단계·체크포인트는 이미 구현돼 있다. 시간 초과를 줄인 성과와 분석 내용의 정확도는 별도로 평가한다. 입력 자료, 프롬프트, 사고 예산, 모델 크기의 영향 역시 아직 분리 측정하지 않았다.

## 참고할 저장소와 가져올 부분

### 1. LightRAG — 그래프와 원문을 함께 검색

[저장소](https://github.com/HKUDS/LightRAG) · [확인한 검색 코드](https://github.com/HKUDS/LightRAG/blob/453dce83d6d0354a06e46c8d4029a0895c4e054b/lightrag/operate.py#L5310)

확인한 구현: local은 개체 중심, global은 관계 중심으로 검색한다. `mix`는 두 경로에 원문 청크의 벡터 검색을 추가한다. 이후 예산에 맞춰 문맥을 구성하며 실제 포함된 청크에 reference ID를 붙인다. 검색 문맥과 구조화된 원자료를 함께 반환한다. [문맥 조립 코드](https://github.com/HKUDS/LightRAG/blob/453dce83d6d0354a06e46c8d4029a0895c4e054b/lightrag/operate.py#L5993)

Backspace 적용 제안: 누적 Material Network를 **관련 원문을 찾는 색인**으로 활용한다. 개념 주변의 원문과 문항 전체를 닮은 원문을 합쳐, 중복 제거·재정렬 후 분석 모델에 전달한다. 작은 자료집에서는 키워드 검색을 기준선으로 먼저 비교한다. 검색 실패 때 그래프 관계를 사실로 대신 공급하지 않는다.

주의: 검색 그래프와 문항의 인과·사고 그래프는 역할이 다르다. 이 구현의 관계 중복 병합에는 정렬된 양 끝점이 쓰인다. 방향 있는 생명과학 인과관계나 요구 사고의 선후 관계를 그대로 이 저장 방식에 맡기지 않는다. 그래프와 벡터 검색을 붙였다는 사실만으로 답안 정확도가 올라간 것은 아니다.

우선순위: 높음. 전체 서버 도입보다 검색 문맥 계약을 먼저 가져온다.

### 2. Ragas — 주장 단위 근거 검증과 정답 비교

[저장소](https://github.com/vibrantlabsai/ragas) · [확인한 Faithfulness 구현](https://github.com/vibrantlabsai/ragas/blob/298b68274234c060deacab3cf5fb52aa3a20e885/src/ragas/metrics/collections/faithfulness/metric.py)

확인한 구현: 답변을 작은 주장으로 나눈 뒤 문맥이 각 주장을 뒷받침하는지 평가한다. 아무 주장도 추출되지 않으면 NaN을 반환한다. Factual Correctness는 검토된 참조 답변과 생성 답변의 주장 겹침을 precision/recall/F1로 비교한다. [정답 비교 설명](https://github.com/vibrantlabsai/ragas/blob/298b68274234c060deacab3cf5fb52aa3a20e885/docs/concepts/metrics/available_metrics/factual_correctness.md)

Backspace 적용 제안: 검증을 두 갈래로 둔다. (a) 인용이 주장을 실제로 지지하는가, (b) 검토된 정답·채점 기준의 필수 기작을 포함하는가. `supported / contradicted / insufficient_evidence`와 이유·출처를 저장한다. 관계는 주어·관계·목적어·조건·방향을 포함한 문장으로 검토한다. 빈 결과·파서 실패는 성공으로 계산하지 않는다.

주의: 자료 자체가 틀렸다면 높은 faithfulness도 과학적 정답을 보장하지 않는다. 짧고 안전한 답변은 근거 점수가 높아도 필요한 설명을 빠뜨릴 수 있다. LLM 채점에는 교사 검수 답안과 일부 사람의 재검토가 필요하다. 같은 모델의 자기 점수만으로 개선을 선언하지 않는다. 기존 `explodinggradients/ragas` 주소는 이동 응답을 반환해 현재 소유자 경로를 확인했다.

우선순위: 가장 높음. 라이브러리 전체보다 주장·근거·필수 요소 평가 계약을 먼저 만든다.

### 3. DSPy / GEPA — 실패 사례에 근거한 오프라인 개선

[저장소](https://github.com/stanfordnlp/dspy) · [확인한 GEPA 설명](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/docs/docs/diving-deeper/gepa-in-depth.md)

확인한 동작: 후보 프로그램을 평가하고, 실패 추적과 자연어 피드백을 reflection 모델에 전달해 지시문 후보를 개선한다. 평가 모델과 지시문 개선 모델의 역할을 분리한다. 단순 점수보다 구체적인 오류 설명을 metric의 feedback으로 전달할 수 있다. 평가 호출 예산을 제한할 수 있다.

Backspace 적용 제안: “산소 감소를 전자 전달의 완전 중단으로 단정했다”, “양성자 기울기를 빠뜨렸다”, “인용이 part_of를 지지하지 않는다” 같은 검수 피드백으로 문항 분석·관계 추출·계획 생성 프롬프트를 각각 개선한다. 최적화는 매 문항 처리 중에 하지 않고 오프라인으로 수행한다.

주의: 확인한 문서에서는 valset을 생략하면 trainset을 재사용한다. 별도 검증셋을 명시하고 최종 시험셋은 최적화에 노출하지 않는다. 평가 기준이 부실하면 그 기준을 잘 맞추는 프롬프트가 생길 뿐이다. 시작부터 GEPA를 돌리기보다 사람이 검토한 실패셋과 수동 프롬프트 기준선을 먼저 만든다.

우선순위: 평가셋 확보 직후 높음. 검색 시스템을 대신하는 도구는 아니다.

### 4. DeepTutor — 학습 목표·선수 관계·학습 기록의 분리

[저장소](https://github.com/HKUDS/DeepTutor) · [확인한 데이터 구조](https://github.com/HKUDS/DeepTutor/blob/f07029cfcf2c8dfccdb671cdfc343db8334f5741/deeptutor/learning/models.py)

확인한 구현: KnowledgePoint에는 선수 목표와 자료 출처, LearningModule에는 목표 문장이 있다. 답안 시도와 잘못된 문항으로 무효화된 시도를 구분한다. 선수 관계의 자기 참조·없는 ID·순환을 검사한다. [관계 검증](https://github.com/HKUDS/DeepTutor/blob/f07029cfcf2c8dfccdb671cdfc343db8334f5741/deeptutor/learning/objective_relations.py)

Backspace 적용 제안: `개념 복습` 대신 목표·실제 과제·필수 답안 요소·완료 조건·자료 위치·문항 ID를 저장한다. 계획 변경 기록과 실제 학생 답안 기록을 분리한다. 학생 답안이 들어온 뒤에만 관찰된 성취 정보를 사용한다.

주의: 확인한 선수 관계 모듈은 구조 메타데이터이며 아직 학습이나 검색을 제어하지 않는다고 명시한다. 점수 정책은 최근 답안의 가중 정확도와 적은 시도 수에 대한 상한이다. 그것이 검증된 학습 능력 추정이라는 뜻은 아니다. 학생 자료가 없을 때 `0점/미숙달`을 부여하지 않고 미관찰로 둔다. 대규모 교육 워크스페이스 전체보다 이 데이터 분리가 지금 목적에 맞는다.

우선순위: 계획 개선에 높음.

### 5. Docling — 텍스트·표·그림·위치가 남는 문서 표현

[저장소](https://github.com/docling-project/docling) · [문서 표현](https://github.com/docling-project/docling/blob/d15cf10c26cf33c54ef2779a1fd9d4e3066d07e0/docs/concepts/docling_document.md) · [확인한 변환 코드](https://github.com/docling-project/docling/blob/d15cf10c26cf33c54ef2779a1fd9d4e3066d07e0/docling/document_converter.py)

확인한 설명·구현: 여러 입력 형식을 변환하고 텍스트·표·그림·문서 계층·가능한 위치 정보와 provenance를 문서 표현에 담는다. 본문 트리의 순서로 읽기 순서를 표현한다.

Backspace 적용 제안: `source → page/slide → block` 단위로 원문, 표 구조, 그림 참조, bbox, 읽기 순서, 해시를 보존한다. 공통 지문·그림·다음 페이지의 선택지가 빠진 문항은 분석 전에 보완 대상으로 분류한다. 그림이 필요한 문항에는 별도의 시각 입력 처리가 필요하다.

주의: 파싱 성공이 생명과학 그림 해석 성공은 아니다. 한국어 학교 시험지의 이단 편집·수식·표·그림 표식을 실제 자료에서 원본과 대조해야 한다. 텍스트 청크만 넘기면 누락 문제가 그대로 남는다.

우선순위: 실제 PDF/PPT/스캔 입력을 평가할 때 높음. 현재 합성 TXT 품질 문제는 이것만으로 해결되지 않는다.

### 6. HippoRAG — 여러 자료를 연결하는 검색

[저장소](https://github.com/OSU-NLP-Group/HippoRAG) · [확인한 검색 파이프라인](https://github.com/OSU-NLP-Group/HippoRAG/blob/2bfd831417202b49cda9da7973e141a456e16872/src/hipporag/HippoRAG.py#L704)

확인한 구현: 관련 사실 검색·필터링, passage 점수, Personalized PageRank로 원문을 찾는다. 유효한 사실이 없으면 dense passage retrieval로 돌아간다. 원문 metadata와 그래프 seed를 반환하고 index manifest를 확인한다.

Backspace 적용 제안: 한 학습지의 산소 설명, 다른 PPT의 전자 전달계, 별도 자료의 ATP 합성 설명처럼 여러 자료를 건너 찾아야 하는 사례에 검색 후보로 비교한다. 색인에 문서 버전·추출기·임베딩 설정을 기록하는 방식도 참고한다.

주의: 확인한 PPR은 `directed=False`로 연관성을 전파한다. 검색의 관련성 점수와 인과적 방향·답안의 논리적 지지는 다르다. 이것으로 Teacher Signature를 채굴하지 않는다. 작은 자료집에서 단순 검색보다 유리한지는 미검증이다.

우선순위: 자료가 커지고 다중 자료 검색 실패가 확인될 때 비교 후보. LightRAG와 함께 처음부터 두 검색 엔진을 모두 넣을 필요는 없다.

### 7. Microsoft GraphRAG — 원문에서 그래프·보고서까지의 출처 구조

[저장소](https://github.com/microsoft/graphrag) · [확인한 출력 스키마](https://github.com/microsoft/graphrag/blob/769542fbf1d8e5b4c6a8677fefc34621c87894c5/docs/index/outputs.md)

확인한 설명: document·text unit·entity·relationship·community report를 구분하고 그래프 구성요소에 원문 text unit 참조를 남긴다. 기본 entity 유형은 생명과학 개념 분석용이 아니므로 설정을 바꿔야 한다.

Backspace 적용 제안: 원문 근거와 자료 관계, 집계된 Teacher Model을 서로 다른 데이터층으로 두는 참고 구조다. 요약만 남기지 않고 원문까지 내려갈 수 있도록 한다. 집계 보고서를 문제별 분석의 대체물로 사용하지 않는다.

주의: 확인한 README는 현재 주로 유지보수 단계이고 새로운 기능이나 PR을 받지 않는다고 안내한다. 색인 비용과 도메인 프롬프트 튜닝도 명시한다. [확인한 안내](https://github.com/microsoft/graphrag/blob/769542fbf1d8e5b4c6a8677fefc34621c87894c5/README.md#L4)

우선순위: 스키마 참고. 현재 MVP의 핵심 의존성으로 먼저 선택할 이유는 약하다.

## 제안하는 단일 파이프라인

다음 흐름은 위 구현에서 가져올 부분을 조합한 **Backspace 설계 제안**이다. 아직 구현하거나 성능을 측정한 결과가 아니다.

```text
원본 보존 + 문서 블록 추출
    ↓
문항 완전성 확인: 공통 지문·표·그림·선택지·페이지 연결
    ↓
학습자료 원문 검색: 개념 주변 + 키워드/벡터 → 중복 제거·재정렬
    ↓
답안 필수 요소와 요구 사고 분석: 조건·기작·관찰·성공 기준
    ↓
의미 검증: 근거 지지·필수 요소 누락·관계 방향·과도한 단정
    ↓
오류가 있으면 부족한 근거 재검색 + 제한된 수정 1회
    ↓
검증 상태를 보존한 문항별 그래프 조립
    ↓
반복 패턴 집계 + 구체적 연습 과제 생성 + 계획 버전 저장
```

원문에서 곧바로 얇은 그래프를 만들며 내용을 버리지 않는다. 먼저 사용자에게 검토 가능한 답안 요소와 관계 설명을 만들고 그 결과를 그래프로 표현한다. 내부 사고 원문을 수집할 필요는 없다. 모델은 의미 분석을 담당하고, 프로그램은 ID·출처·범위·집계를 관리한다.

분석 결과에는 다음 필드를 추가하는 것이 좋다.

| 데이터층 | 최소 추가 정보 |
|---|---|
| SourceBlock | 원문 위치·종류·내용·해시·표/그림 참조·추출 누락 여부 |
| ConceptMention | 개념 ID와 별도로 언급 위치·문맥·연결 후보·병합 검토 상태 |
| MaterialClaim | 주어·술어·목적어·성립 조건·출처·검증 상태 |
| QuestionDemand | 문항 고유 목표·operation code·입력 정보·답안 산출물·필수 요소·근거 |
| DemandRelation | 관계 방향·뜻을 설명하는 문장·근거·검증 상태 |
| Review | 오류 종류·이유·근거 부족 여부·수정 전후 버전 |
| Signature | 추상 사고 패턴과 내용별 구체 사례·서로 다른 문항 support·적용 가능 문항 분모·검토 상태 |
| PlanTask | 목표·과제·선수 목표·자료 위치·근거 문항·평가 기준·진행 상태·생성 근거 버전 |

자료의 과학적 기작과 문제의 요구 사고는 서로 다른 관계층이다. “전자 전달 감소 → 기울기 형성 감소”와 “조건 비교 → 기작 설명”을 같은 edge 의미로 합치지 않는다. 공통 Concept ID로 연결하되 문항 단계의 ID와 경로 채굴 범위는 문제 안에 유지한다.

자료에 없는 지식을 모델이 보충하면 `domain_knowledge_needs_review`처럼 구분한다. 지시문이 요구하는 행동의 근거는 문항에서, 과학적 설명의 근거는 학습자료/검토된 참조에서 찾는다. 인용은 모든 관계를 지지하는 만능 근거가 아니다. 개념 병합은 정확한 alias로 먼저 처리하고 의미 후보는 검토 전 자동 통합하지 않는다.

패턴 집계는 현재의 추상 사고 코드 패턴을 유지하되 구체적 내용·조건·산출물 예시를 함께 제시한다. 같은 프롬프트가 만들어 낸 일반적인 6단계 경로가 많이 반복된다고 교사의 특징으로 확정하지 않는다. 출제 의도는 문항에서 관찰한 요구의 가설이며, 교사의 사적 의도나 학생의 실제 능력을 뜻하지 않는다.

## 같은 샘플에서 기대하는 변화

현재 합성 산소·ATP 문항의 출력은 일반적인 사고 이름과 동일한 복습 활동이다. 다음은 검수 목표 예시이며 새 모델 결과가 아니다. 추가 기작은 현재 3문장 학습자료에 모두 들어 있지 않으므로 보완 자료 또는 검토된 참조 답안이 필요하다.

- 관찰: 조건 B에서 산화적 인산화에 의한 ATP 생성이 감소했다.
- 비교 목표: 조작한 산소 공급과 관찰된 ATP 생성량을 구별한다.
- 필수 설명: 산소의 최종 전자 수용체 역할을 전자 전달, 양성자 기울기 형성, ATP 합성과 연결한다.
- 검토 사항: 산소 공급의 감소만으로 전자 전달이 완전히 멈췄다고 단정하지 않는다. 조건부 설명을 검토된 정답 기준과 맞춘다.
- 실제 과제: A/B 조건표 작성 → 기작 연결도를 빈칸 없이 작성 → 연결을 포함한 서술형 답안 제출.
- 완료 기준: 단순한 “산소가 줄어서 ATP가 준다”를 넘어서 필수 연결을 포함하고 각 관계의 방향과 조건이 맞는다.

이런 구체성이 그래프에도 남아야 한다. 사고 코드는 비교·원인 추론 같은 공통 태그로 사용하고, 문항 고유 내용의 대체물로 쓰지 않는다.

## 검증 순서와 채택 기준

먼저 실제 제공 자료에서 소규모 검수 문항셋을 만든다. 최초 20~30문항은 실패 유형을 찾는 탐색용 제안이며 통계적으로 일반화된 성능 증거는 아니다. 그림·표·공통 지문·조건부 기작·여러 자료의 연결 문제를 포함한다. 원문·검토 정답·필수 요소·금지할 단정·근거 블록을 사람이 확인한다.

다음 실험은 같은 문항·같은 자료·같은 출력 목표로 비교한다.

| 실험 | 확인할 역할 |
|---|---|
| A: 강한 모델 단독 | 사용자 기대 수준의 기준선. API 접근이 가능한 모델에서 실제 실행해야 한다. |
| B: 같은 NVIDIA 모델 단독 | 모델 차이와 구조 차이를 구분. 전체 자료가 문맥에 들어가는 부분집합도 비교한다. |
| C: 현재 파이프라인 | 현재 결과의 출발점 |
| D: 내용 보존 + 자료 검색 | 검색과 풍부한 표현이 만드는 차이 |
| E: D + 의미 검증·제한 수정 | 검증이 오류를 줄이는지, 올바른 답변을 망치지는 않는지 |
| F: E + 오프라인 프롬프트 개선 | GEPA 등을 도입할 추가 가치 |

정답·필수 기작 coverage, unsupported/contradicted 주장, 관계 의미·방향, 문항 누락, 계획의 구체성과 목표 대응을 별도 측정한다. 검색에는 검수 근거 블록 recall을 사용한다. 의미 채점은 참조 답안과 사람이 확인한 루브릭을 중심으로 하고 모델 판정은 보조로 쓴다. 토큰 수·호출 수·지연·실패율도 같이 기록한다.

같은 문항에서 검색 유무와 리뷰 유무를 각각 제거해 효과를 분리한다. 모델·사고 예산·출력 예산을 기록하며, 품질 실험과 동일 비용 실험을 구분한다. 초과 예산과 실패도 분모에 포함한다. 같은 시험/원자료의 유사 문항이 학습·검증·시험에 걸쳐 새지 않게 분리한다. 프롬프트 개선에 최종 시험 정답이나 리뷰를 사용하지 않는다.

채택 조건은 검토된 미사용 문항에서 현재 방식/같은 모델 단독보다 유의미한 개선이 관찰되고 비용·지연의 증가를 설명할 수 있는 것이다. 강한 모델 단독을 이기지 못하면 품질 격차와 비용의 이득을 그대로 보고한다. 아직 어떤 저장소도 이 과제에서 우월성을 입증하지 않았다.

## 다음 구현에서 먼저 바꿀 부분

1. `question()` 입력에 검색된 학습자료 원문과 출처 추가, 답안 필수 요소·조건·문항 고유 목표 저장.
2. MaterialClaim/DemandRelation의 의미 검토 추가. 현재 잘못된 관계는 검토 전 학습 근거로 쓰지 않음.
3. 개념별 대응을 전체 사고 코드가 아닌 실제 연결 단계·설명 목표에서 계산.
4. `generate_plan()`을 목표·과제·완료 기준 생성으로 교체하고 검토된 목표에서만 생성.
5. 위 수정의 작은 기준선 비교를 수행한 뒤 검색 엔진·최적화기 도입 여부 결정.

우선 참고 조합은 **Ragas의 평가 계약 + LightRAG의 원문 검색 + DeepTutor의 계획 데이터 구조**다. DSPy는 검수셋이 생긴 뒤 최적화에, Docling은 실제 문서의 입력 품질에, HippoRAG는 다중 자료 검색에, GraphRAG는 출처 스키마에 참고한다. 이 조사에서 확인한 선택 파일에는 Backspace의 Teacher Reasoning Signature를 그대로 구현한 기능은 없었다. 그 부분은 문항 요구 분석과 검수 기반으로 직접 설계해야 한다.
